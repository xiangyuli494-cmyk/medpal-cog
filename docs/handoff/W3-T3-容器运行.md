## 0 一句话

镜像、编排、启动、探活、持久化探针、CI 构建作业都在仓库里；本机没有 Docker daemon，
真实构建日志由 CI 与 T1 的机器产出。**这一版按 #36 的评审意见改了三处硬伤：**
① 台账口径从「62 / 69」更正为 **70 张卡 / 37 条活跃三元组**；

## 3 T1 在机器上要跑的五步

在仓库根目录执行（不是 `deploy/` 里）：

```bash
# 1) 构建（这一步就是 W3 要的「docker build 实机构建」证据）
docker build -f deploy/Dockerfile -t medpal-cog/mcp:0.1.0 .

# 2) 起服务（前台看日志，不要 -d，先确认建库和灌卡都过了）
docker compose -f deploy/docker-compose.yml up --build

# 期望看到的关键行（首次启动）：
#   [entrypoint] 种子库不存在，首次建库：/app/mcp-server/data/medpal.db
#   [entrypoint] 首次建库，灌入 data/samples（70 份样本里 3 份解析不出，实得 70 张卡）
#   样本 73 份 | 入库 70 行 | 导出 70 张卡
#   [entrypoint] 台账 70 行 | transport=streamable-http host=0.0.0.0 port=8090
#   INFO:     Uvicorn running on http://0.0.0.0:8090

# 3) 另开一个终端，从宿主验探活（等价于 §10.5 M-2）
curl -s -X POST http://127.0.0.1:8090/mcp \
  -H "content-type: application/json" \
  -H "accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"0"}}}'
# 必须回 serverInfo.name=medpal-cog

# 4) 确认 healthcheck 自己判绿（现在它同时要求 assets ≥ 61，initialize 必须回 serverInfo.name=medpal-cog）
docker inspect -f '{{.State.Health.Status}}' medpal-mcp    # healthy

# 5) 两次启动验证（评审 P1 要求的那一项：重启不许抹掉运行期资产、不许把版本退回 v0.9）
docker cp deploy/persist_probe.py medpal-mcp:/app/persist_probe.py
docker exec medpal-mcp python /app/persist_probe.py --write
docker restart medpal-mcp
# 等 healthy
docker inspect -f '{{.State.Health.Status}}' medpal-mcp
docker exec medpal-mcp python /app/persist_probe.py --verify   # 必须打印 [probe] OK
```

## 4 验收口径（五项，缺一项不算 T3-2 完成）

| # | 判定 | 期望 | 证据 |
| --- | --- | --- | --- |
| 1 | 镜像构建成功 | 退出码 0，镜像 `medpal-cog/mcp:0.1.0` 存在 | `docker images \| grep medpal-cog/mcp` 截图 |
| 2 | 容器起在 8090 且 `healthy` | `docker inspect` 的 `State.Health.Status=healthy` | 截图 |
| 3 | MCP 真响应 | `initialize` 回 `serverInfo.name=medpal-cog` | curl 输出截图 |
| 4 | 资产不是空的（也不是「少卡」） | 容器内 `asset = 70`、`triple_active = 37` | `docker exec medpal-mcp python -c "import sqlite3;c=sqlite3.connect('/app/mcp-server/data/medpal.db');print(c.execute('select count(*) from asset').fetchone(), c.execute(\"select count(*) from triple where status='active'\").fetchone())"` → `(70,) (37,)` |
| 5 | 两次启动持久化 | `persist_probe.py --verify` 打印 OK：运行期上传的资产还在、当前版本仍是 v1.0、旧快照未变 | 第 3 节第 5 步输出 |

第 4 项是这张卡最容易糊过去的地方，也是上一版写错的口径：端口通、healthy 都绿，但容器里 asset=0 照样「健康」。
现在的写死口径是：**73 份样本，3 份解析不出（`pdf_07_encrypted` / `pdf_08_scan_image_only` / `pdf_10_blank`），
入库 70 行、导出 70 张卡、活跃三元组 37 条**。上一版写的 62 是 `data/asset-cards/` 里旧卡的文件数、69 是本机少装
`openpyxl` 时 `reference_ranges.xlsx` 解析失败少了一张卡（补装依赖后复测就是 70），都不是入库数。

## 5 已知坑（T1 大概率会撞，提前写在这）

1. **拉基础镜像卡住**：`python:3.12-slim` 走国内镜像源。可用（10-28 实测通）：`https://docker.1ms.run`、`https://docker.m.daocloud.io`；不可用：中科大源、dockerproxy.cn（详见 `docs/env.md` §1.4）。
2. **代理没豁免回环**：宿主设了全局代理时，`curl 127.0.0.1:8090` 会被代理劫持成 connection refused。容器内探活已显式禁代理；宿主 curl 记得 `NO_PROXY=127.0.0.1,localhost`。
3. **8090 被占**：宿主已有服务占 8090 时 compose 起不来，改 `ports` 左侧端口，或先 `netstat -ano | findstr 8090`（Windows）/ `ss -lntp | grep 8090`（Linux）。
4. **卷与重灌**：`medpal-data` 卷挂到 `/app/mcp-server/data`，**空卷**才会触发 seed + ingest（约 5-15 秒）；**已有卷不会再灌**，库里资产与版本都保留。要强制重建才设 `MEDPAL_INGEST=rebuild`（会覆盖台账，慎用）。
5. **换 Python 版本**：3.13 及以上会让 pymupdf 装不上（静默跳过），PDF 卡解析失败。要升 3.13 必须先改 `requirements.txt` 的条件并另开 PR。
6. **本机 69 vs 容器 70**：不是镜像问题，是宿主缺 `openpyxl`。`pip install "openpyxl>=3.1"` 之后本地也是 70；CI/容器装的是 `requirements.txt`，天然是 70。
7. **资产卡里的 `source.path` 是绝对路径**（提交里写的是 `E:\deepseek-data\...`）。换机器或进容器重跑 `ingest_all` 会被重写成新路径——既有数据卫生问题，不在本 PR 修（牵动 62 个文件）。

## 6 本机验证到哪一步（写在这，免得当成已验证）

本机 Windows **没有 Docker daemon**（`docker` 不在 PATH、未装 Docker Desktop、无 WSL 发行版），
`docker build` / `compose up` / 容器内探针**不是我在本机跑的**，由 CI 的 `docker` job 与 T1 的机器执行。
本机能验、且已经验过的：

- `python tools/ingest_all.py`：`样本 73 份 | 入库 70 行 | 导出 70 张卡`，库内 `asset=70 / triple_active=37`（补装 `openpyxl` 后复测，与 T2 在干净副本里的实测一致）。
- 起一个完整库（`MCP_TRANSPORT=streamable-http`，8090）→ `python deploy/healthcheck.py`：`[healthcheck] OK serverInfo.name=medpal-cog assets=70`，退出码 0。
- 起一个只有种子资产（`assets=1`）的库 → 同一个脚本：`[healthcheck] FAIL 台账 assets=1 < 61`，退出码 1（空台账不再判健康）。
- `tools/ingest_all.py` 在 `data/samples` 为空时返回 1（回归测试 `tests/test_deploy_guards.py` 锁住），entrypoint 的 `|| exit 1` 这才真的会触发。
- 已有的 v1.0 库上再跑一次 `ingest_all`：`current_version` **仍是 v1.0**，`v0.9` 快照的 `triple_count/manifest_hash` 未变（版本不再被写回 v0.9）。
- `bash -n deploy/entrypoint.sh` 通过（shell 语法无错）；`ruff` 全过；`pytest tests` 全绿。
- 没做的：`docker build`、`docker compose up`、镜像层体积、容器内第 4/5 项（都依赖 daemon）。这些由 `.github/workflows/docker.yml` 每次 PR 验证：构建 → 起容器 → 等 healthy → 宿主 curl → 容器内 asset ≥ 61 → 重启后持久化验证。**这条 job 绿了，才说明 Dockerfile 至少在 Linux 上构建得出来、跑得起来、重启不丢数据。**
