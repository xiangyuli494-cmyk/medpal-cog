# 进化预演：v0.9 → v1.0（为什么决策会变）

> 对应 issue #22（W2-T1 主智能体 v1 与进化预演）。结论先行：**本体真的提交了一个新版本，
> 同一个问题在新旧两版上的答案不同，差异可以逐条追到新增的三元组上。**
> 证据文件：[agent/sessions/evo-w2-01.json](../agent/sessions/evo-w2-01.json)。

## 1. 评委要看到的三个数

| 项 | v0.9 | v1.0 | 命令 |
| --- | --- | --- | --- |
| 版本行（version 表） | 1 行（v0.9） | 2 行（v0.9 / v1.0，is_current 指向 v1.0） | python mcp-server/seed.py --reset && python tools/ingest_all.py |
| 活跃三元组 | 37 | 61 | 同上，打印「本体进化: v0.9 → v1.0 … 版本内 61 条」 |
| 快照文件 | ontology_v0.9.jsonl（37 行） | ontology_v1.0.jsonl（61 行） | python tools/onto_diff.py --from v0.9 --to v1.0 |

差分：**added 24 / removed 0 / modified 0**（24 = 20 条结构关系 + 4 条工具链提案）。
提交后的 manifest 哈希：4dbb059c8a921d6d。同一份语料在干净副本上重跑得同一哈希，
说明这批新增不是随机生成，也不是「每次跑都不一样」。

## 2. 同一个问题，两版两种答案

问题（见 evo-w2-01.json 的 question）：

> 患者乏力、面色苍白，怀疑缺铁性贫血，应该挂哪个科室、要做哪些检查？

| | v0.9 | v1.0 |
| --- | --- | --- |
| 实体归一 | 「缺铁性贫血」→ 未映射（unmapped） | 「缺铁性贫血」→ ICD-10 **D50.9** |
| 结论 | 科室：未取到 / 检查项：无 / out_of_scope=true | 科室：**血液内科** / 检查项：**血常规、血清铁蛋白、骨髓涂片** / out_of_scope=false |
| 证据 | 0 条 | 12 条锚点（含 AST-2026-691cca#s2.p1.c1 这类来自新文档的锚点） |

## 3. 为什么变了（可追到具体的边）

v1.0 新增 4 份样例文档（data/samples/text/pathway_21..24.md），本体由此长出：

| 病 | ICD-10 | 科室 | 检查项 |
| --- | --- | --- | --- |
| 缺铁性贫血 | D50.9 | 血液内科 | 血清铁蛋白、骨髓涂片、血常规 |
| 甲状腺功能亢进症 | E05.9 | 内分泌科 | 甲状腺功能、甲状腺超声、血常规 |
| 急性阑尾炎 | K35.8 | 普外科 | 腹部超声、血常规 |
| 慢性阻塞性肺疾病 | J44.9 | 呼吸内科 | 肺功能、血常规 |

外加 4 条跨文档关联（may_cause）：消化性溃疡 → 缺铁性贫血、甲亢 → 心房颤动、
急性阑尾炎 → 腹膜炎、慢阻肺 → 肺心病。跨病种关联是本轮唯一的**新知识**：
结构关系（科室/检查）在语料里写得很直白，工具链第一遍就能抽到；
而「溃疡出血久了会贫血」这种跨文档推断，只有把两份文档放进同一个知识图才成立。

别名也跟着版本走：v0.9 只说 K27 那一片（12 条别名，无「缺铁性贫血」），
v1.0 才把 19 条新别名（含全部新病名/检查名/科室名）写进去。
**这不是把答案写死**——v0.9 里本体没有这些节点，别名表也没有，
问题里的词既归不了码、也连不上边，决策链在第一步就断；v1.0 里链路完整，答案自然不同。

## 4. 工具链怎么走的（不是直接改库）

```text
ontology_grow.grow(v0.9 基线)           # 4 份文档 → 20 条结构关系
        ↓
ontology_evolve.add_aliases()           # 19 条别名（跟版本一起发布）
        ↓
onto_propose(asset_ids)                 # 读新文档锚点 → 抽候选 → 写 pending_diff
        ↓  candidates 4 / rejected 40（规则挡下：no_pattern_match / too_short / duplicate）
onto_commit(diff_id, version=v1.0)      # 落库 + 快照 + 版本行 +1
        ↓
store.diff_versions(v0.9, v1.0)         # added 24 / removed 0 / modified 0
```

两个必须显式处理的坑，写在这里免得下一个人重踩：

1. onto_commit 不带 version= 时会走 _bump()，把 v0.9 推成 **v0.10**，不是 v1.0。
   赛题口径要 v1.0，所以 ontology_evolve.py 把版本号钉死传进去。
2. onto_propose 只认「别名表里已有的实体」。先 propose 再补别名，
   候选会整条判成 entity_unresolved 被丢掉——顺序必须是**先长结构、再补别名、最后 propose**。

## 5. 复现（三条命令，不碰交付库）

```bash
python mcp-server/seed.py --reset          # v0.9 种子库
python tools/ingest_all.py                 # 建 74 张资产卡 + 长本体 + 提交 v1.0
python tools/make_evo_evidence.py          # 两版对比 + 4 份会话（写 agent/sessions/）
```

make_evo_evidence.py 在 tmp/evo-evidence/ 下现建两个状态（A 态只有 v0.9 语料，
B 态是交付库副本），跑完即弃；交付库的 trace 表不会被评测污染。
每份会话都带 ontology_version、tool_calls、evidence 与三行 expected_tail，
tests/test_agent_config.py::test_sessions_match_output_contract 会逐份校验。

## 6. 这与「分数变化」的关系

评测集 20 条在 v1.0 上仍是六项 100%（python eval/run_eval.py）。
但这不是「进化」的证据——**固定题库不变、本体变了还能 100%，说明的是没有回归**。
真正的证据是上表那一条：v0.9 答不出的问题，v1.0 答得出，且能说出是因为哪几条边。
下一批评测（W2-T3，20→24 条）会把这类「新病种」题正式收进题库，
届时同批评测在 v0.9 与 v1.0 上的分数差才是可量化的进化指标（当前 20 条里没有新病种题）。

## 7. 已知边界

- **只有 4 个新病种**：37→61 是「1.65 倍」，不是「知识覆盖医疗」；语料全是合成样例，不含真实病历。
- **候选淘汰率高**：40 条被规则挡下（多数是与 grow 重复或句式不匹配），
  说明规则抽取器只认写明的关系，隐性推断（如「长期溃疡出血 → 贫血」）要靠人写进文档才会被抽到。
- **不做诊断结论**：新增的 may_cause 只用于提示「需要排查」，不改变主述结论，
  也不产出确诊用语——与方案 §6 的边界一致。
- **Nexent 侧尚未接入 v1.0**：本文件的证据来自工具链回放（确定性引擎），
  平台内的主智能体读取的是同一个 MCP Server，配置无需改动，但 R5 的实跑记录要等下一轮补（issue #6）。
